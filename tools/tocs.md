它们虽然都能叫“目录”，但处在不同层级，作用完全不同。

| 名称         | 所在位置                    | 内容                           | 作用                     |
| ------------ | --------------------------- | ------------------------------ | ------------------------ |
| 表1          | BIG 文件头之后，通常 `0x20` | `起始资源ID + 数量 + TOC起点`  | 逻辑资源 ID → 表2下标    |
| 表2          | BIG 文件头指定的位置        | `group_hash + resource_offset` | 表2下标 → 物理资源块     |
| `0x69e5d35c` | BIG 数据区中的普通资源      | `数量 + uint32 句柄数组`       | 逻辑资源/对象 → 资源句柄 |

可以理解成三步：

```
0x69e5d35c 内的句柄
        ↓
表1：把逻辑资源 ID 映射成表2下标
        ↓
表2：找到 group_hash 和物理 offset
        ↓
实际资源数据
```

以 Pack4 为例：

```
0x69 文件中的句柄：
0x030002E1

取低 15 位：
0x02E1

查表1：
0x02E1 → 表2第 482 项

查表2：
表2[482] =
group_hash  0xF4E02223
offset      0xDBE6
```

所以区别是：

```
表1：索引到索引
表2：索引到物理资源
0x69：保存逻辑资源句柄
```

`0x69e5d35c` 里的内容没有直接存储：

```
group_hash
resource_offset
resource_size
```

所以它不是 BIG 主 TOC。它更像游戏运行时使用的“逻辑资源句柄目录”。

另外还有一层：

```
AggregateResource 内部 TOC
```

它负责：

```
聚合资源句柄 → 子资源 offset / size / mime
```

因此完整层级大概是：

```
0x69 句柄表
    ↓
BIG 表1
    ↓
BIG 表2
    ↓
聚合资源内部 TOC（仅聚合句柄需要）
    ↓
最终子资源
```
